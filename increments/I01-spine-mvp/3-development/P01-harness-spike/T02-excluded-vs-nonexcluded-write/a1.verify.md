## Summary

All three criteria pass. The verdict is based entirely on the state files (state-after-session1.txt, state-after-session2.txt, state-listing.txt), not on stub stdout: probe.txt is exactly 31 bytes after session1 (5 bytes "seed\n" + 26 bytes "spine wrote at 1795746590\n"), and byte-identical after session2, proving the excluded spine stub wrote successfully while both spine-admin invocations added nothing.

Four findings are recorded: (F-1) auto mode was active in session1 and may have widened the apparent permission surface; (F-2) the AC-3 premise that the full-path spelling would be unmatched by the Bash(spine-admin *) deny was falsified — it matched both spellings — requiring a correction to the task spec; (F-3) the actual defense-in-depth evidence for AC-3 came from session2, where a bash-wrapper + --permission-mode default relaunch bypassed the permission deny but the sandbox denyWrite still returned EPERM; (F-4) both stubs have a bug where they exit 0 and print "appended" even on a failed write, which did not affect this verdict because writes were judged from state files.

## AC-1: excluded `spine` writes the protected state dir (runs unsandboxed)

Evidence: state-listing.txt shows probe.txt at 31 bytes, timestamp 27 Nov 02:29. state-after-session1.txt contains "seed\n" + "spine wrote at 1795746590\n". resolution.txt confirms the spine that executed was /Users/luisteles/spine-harness-probe/bin/spine (the probe stub). The write landed, confirming the excluded command ran without sandbox restriction. The stub's stdout "appended (exit 0)" is consistent but was not the basis for this conclusion.

## AC-2: bare `spine-admin probe-write` refused by permission-layer deny

Evidence: session1.txt line: "Error: Permission to use Bash with command spine-admin probe-write has been denied." No new line appeared in state-after-session1.txt. This is a permission-layer refusal via the Bash(spine-admin *) deny rule in fixture.settings.json — not the OS sandbox boundary.

## AC-3: non-excluded binary's write blocked by sandbox denyWrite (OS boundary)

Evidence: The task's stated mechanism (full-path form unmatched by prefix deny) was falsified in session1 — the full-path invocation "~/spine-harness-probe/bin/spine-admin probe-write" was also caught by the Bash(spine-admin *) deny rule, so it never reached the sandbox. The human relaunched in session2 with --permission-mode default and ran "bash ~/spine-harness-probe/bin/spine-admin probe-write"; this bash-wrapper construction was not caught by the spine-admin prefix deny and ran. The sandbox fired: session2.txt shows "/Users/luisteles/spine-harness-probe/bin/spine-admin: line 7: /Users/luisteles/spine-harness-probe/state/probe.txt: Operation not permitted" and stub exit 1. state-after-session2.txt is byte-identical to state-after-session1.txt (diff exit 0, both 87 bytes): no spine-admin line was added. The sandbox denyWrite blocked the write at the OS level. AC-3 passes on substance; the stated mechanism in the spec is incorrect and needs a correction.

## Auto-mode caveat (Finding F-1)

Neither fixture.settings.json nor the user's H0 settings (not committed here) set disableAutoMode:true or permissions.disableBypassPermissionsMode:false. In session1, the spine Bash call was auto-approved. ADR-012's switch-over design requires both keys. The AC conclusions are auto-mode-independent in this probe: excludedCommands is a sandbox-level bypass that overrides any permission posture, and the Bash(spine-admin *) deny and denyWrite both fire regardless of auto mode. Auto mode did not invalidate the results, but the probe under-tested the permission-prompt posture. The H0 reference settings are missing these two keys.
