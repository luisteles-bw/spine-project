## Summary

All four acceptance criteria pass. Every refusal string and corroborating control file was confirmed
by grep/wc against the actual captured output — no prose claim was taken on trust alone.

**AC-1 (Bash denyWrite):** `echo >> state/probe.txt` produced "Operation not permitted", `append
exit=1`, and `lines before=1 after=1`. state-after.txt contains only "seed" (5 bytes) and
state-listing.txt shows probe.txt still at 5 bytes with no other files, confirming the filesystem
was physically unchanged.

**AC-2 (Edit + Write permission deny) — session1 `Create` ambiguity resolved:** In session1 the Edit
tool rendered as `Create(state/probe.txt)`, which is ambiguous (Claude Code renders Edit as Create
when the target does not yet exist in its view, not because the file is absent). Session2 was run
specifically to resolve this: the Read tool confirmed the file exists and contains "seed", then an
Edit (`Update(state/probe.txt)`) was attempted — it failed with the identical
`<tool_use_error>File is in a directory that is denied by your permission settings.</tool_use_error>`
error. The Write tool's refusal (`Write(state/probe2.txt)`) is independently confirmed by the absence
of probe2.txt in state-listing.txt. Together, session1 (Write) and session2 (Read-then-Edit) fully
satisfy AC-2. The `failIfUnavailable: true` sub-clause is **n/a** on macOS tier 1 — per AC-2 text,
this is verified by docs + `doctor` key recognition, not a live probe, and is not a gap.

**AC-3 (nested .env denyRead):** `cat` returned "Operation not permitted" with exit=1; `node -e`
readFileSync returned EPERM with exit=1. Both reads of `secrets/nested/.env` were blocked by
sandbox `denyRead`.

**AC-4 (credentials envVars deny) — cross-session control provenance sufficient:** The first
terminal was lost before the control was captured. The control was obtained in a fresh shell for
session2 and written to token-control.txt by that same shell (`PROBE_TOKEN in launching shell:
should-be-hidden`). Both session1 and session2 show `PROBE_TOKEN=[<unset>]` inside the sandbox.
Both sessions ran under the same fixture (v2.1.325, `~/spine-harness-probe`, same
fixture.settings.json). The cross-session pairing is coherent: the control demonstrates the var was
exported in the launching environment; the two independent sandbox observations both show it absent.
An unset-var explanation would require the var to have been absent in both shells, which is excluded
by token-control.txt. The provenance is sufficient to attribute the absence to `credentials.envVars`
deny.

**Version:** Claude Code v2.1.325 confirmed in both session banners and in version.txt — consistent
across all three sources.
